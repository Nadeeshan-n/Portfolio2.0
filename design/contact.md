# Contact refinement

## Scope and source

The source opened for this request had no Contact section; the earlier combined learning/contact block was already removed. The new Contact section sits after Technical Arsenal and before the existing footer. The dark form screenshot was not available in the active files, so the detailed written brief and current portfolio components guided the implementation. No existing section, shared stylesheet, artwork, navigation, statistics value, or technology asset was edited. The Contact addition is isolated to its HTML block, `contact.css`, `contact.js`, `contact.json`, and one original, lightweight SVG texture.

## Visual system

The introduction uses the existing CONTACT label and jade rule, a Sora 700 heading, and short personal copy. Its GitHub link and the delivery note below Send Message are removed. The optional email row stays hidden until a real recipient is configured, leaving no empty link-row spacing. The form blends into the ivory page background with no visible outer border; a transparent 1px border preserves its existing dimensions and alignment. The ivory 13px rounded inputs retain the existing charcoal, muted green, jade, and border tokens. A six-mark SVG texture sits behind the fields at 4.5–5% opacity. Three faint background marks float only while the section is visible. The submit control inherits the site's existing flat square sketch button, including its charcoal border, hatching, hover/active jade colors, and focus ring. Its arrow icon is removed. The same jade fill, white label and shared sketch accents are shown while delivery is unconfigured; native disabled behavior remains intact. Forced-colors mode retains system button colors and hides decorative marks. No shared button rules change.

At 760px and below, introduction and form stack. A subtle 1px rule in the existing border color divides the introduction from the form at the center of their gap: vertically on desktop, horizontally when stacked. It occupies no layout space. At 520px and below, the name fields and form footer stack. The flight chooses its route from the actual column geometry, rather than assuming section width equals viewport width; a stacked tablet therefore uses the correct edge lane. The controls, live statuses, required states, and error text retain native accessible semantics. Reduced motion disables decorative movement; forced colors hides decoration and provides system-colored field focus and error borders.

## One-time flight

An IntersectionObserver starts the sequence once when at least 18% of Contact is visible. The SVG is completely hidden initially. After a 400ms pause, a 36px hand-drawn paper plane follows the same native SVG path whose stroke is revealed behind it. Flight takes 3.8s with cosine ease-in-out. It arrives at the form's upper right, settles by at most 1.5px and 1 degree, holds for 550ms, then disappears over 650ms while the line erases from destination back to origin. The whole sequence ends at 5.4s and never repeats on scroll, hover, or submission. The mobile plane is 70% size and travels down a clear outer lane beside the introduction.

Active-time accounting pauses the sequence offscreen and when the document is hidden, so returning cannot skip the remaining motion. ResizeObserver updates the SVG viewBox and path while preserving the elapsed sequence. It disconnects after completion. Changing to reduced motion ends the flight permanently; changing back does not restart it. Missing observer, frame, or geometry APIs leave a static Contact section. All SVG decorations are non-interactive and hidden from assistive technology. No animation library, video, GIF, external dependency, storage, or analytics was added.

## Delivery configuration

Neither the current portfolio nor the user supplied a real recipient or form endpoint. The optional destination question received no answer. Therefore, `contact.json` defaults both values to null and the send control stays disabled. The selected delivery note and Contact GitHub link are removed; removing their copy does not configure or enable delivery. Existing hero/footer contact routes are unchanged. This avoids an invented address or a false success state.

A configured email produces a fully encoded mailto draft and explains that the visitor must send it. A configured public HTTPS JSON endpoint enables direct submission, input validation, duplicate-submit prevention, a 15s abort, an announced result, and message retention on failure. Endpoint requests omit credentials. The config fetch is read-only and contains no message content. No real service or email was contacted during QA. Delivery cannot be verified until the owner supplies a destination.

## Verification and limits

`scripts/check-contact.cjs` exercises 11 groups of source-level lifecycle checks: pending/unsafe configuration, associated required errors, malformed visitor email, encoded email drafts, successful endpoint response and busy state, service/network failures, one-time flight phases and reverse erasure, offscreen/hidden-page pause, reduced-motion and unsupported API fallbacks, and stacked-tablet/live-resize routing. All requests and SVG geometry APIs are mocked. JavaScript syntax and whitespace checks pass. These checks substantiate lifecycle behavior, not actual browser rendering.

The 12ui workflow was attempted with a generic design prompt that contained no private page image or source. It stopped at a separate sign-in requirement before producing candidates. Thus no 12ui target comparison is available. The managed runtime has no supported browser QA skill, and no preview server or alternative browser was started. Source-derived 1195px desktop and 375px mobile layout studies using the self-hosted Sora font were inspected for spacing and readable text; these are not browser screenshots. Non-Contact HTML was confirmed byte-identical to the published baseline, and existing CSS, JavaScript, data, and artwork remain unchanged. Browser rendering, actual SVG motion, and real message delivery remain unverified.
